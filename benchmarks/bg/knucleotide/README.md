# knucleotide

`setup(n)` (untimed): BG fasta's output for n (10.2·n bytes), generated by each port in its own language with the same algorithm (ALU repeat for 2n, IUB random for 3n, Homo sapiens random for 5n, 60 per line; LCG seed 42, cumulative probabilities in double; checked equal to BG's `fasta-output.txt` at n=1000 and to `benchmarks/bg/fasta` at 2,500,000).
`bench(n)`: the BG program over that text: find `>THREE`, encode its bases, count the 1- and 2-mers (sorted, percentages) and the 5 fragments; returns FNV-1a (32-bit) of the bytes BG prints. n = 500,000 (2.5 M bases; BG: fasta 25,000,000).
Check: n=1000 → 2506903540 = FNV of BG's `knucleotide-output.txt` (every port). n=500,000 → 1583578344.
Run: `node scripts/benchmark-bg.mjs knucleotide` (from the repo root: the C++ and Haskell flags hold paths).

## Ports

All single-threaded: BG's threads/tasks run in order (thread count 1 where the program strides by it).

| port | source | adapted |
|---|---|---|
| c | BG gcc #1 (Zerfas): khash, custom hash `k ^ k>>7` | OpenMP sections in order; stdin → `fgets` over the text; `printf` → `snprintf` + FNV. `khash.h` (klib, MIT) vendored |
| cpp | BG g++ #2 (Saguban): `__gnu_pbds::cc_hash_table`, templated key sizes | `thread_count` 4 → 1; `std::cout` → `std::ostringstream`. pb_ds is libstdc++-only; Emscripten has libc++, so the 155 GCC 16 headers it needs are in `cpp/pbds/` with a small shim (`bits/c++config.h`, `cpp_type_traits.h`, `debug/debug.h`, `tr1/*`). **Bug fix**: BG's key update reads the codes at each window's start, not its end (first windows wrong, last size−1 missing); at fasta 10,000 the 2-mer percentages differ from BG's other programs. Fixed (start at `begin + thread_count + size − nsize`) |
| rust | BG Rust #7: hashbrown, generic key types u8..u64 | tokio_threadpool/futures dropped (jobs in order); `num` → num-traits; hashbrown 0.15 (foldhash); `println!` → `write!` to a String |
| go | BG Go #7 (after C++ #2) | `numCPU = 1`, calc32/calc64 called not spawned; same window bug as C++ #2, same fix; `fmt.Println` → `strings.Builder` |
| swift | BG Swift #2 | `ntasks` 8 → 1, `concurrentPerform`/merge queue → loop; no Foundation (`String(format:)` → `vsnprintf`); **keys Int → Int64**: Int is 32-bit on wasm32 and the 18-mer key is 36 bits (with Int the 18-mer count was wrong) |
| haskell | BG GHC #2: `Data.HashTable.ST.Basic`, keys recomputed per frame | `parallel` dropped, `threads = [0]` (BG 64 strided tables); hashtables + hashable are not in GHC's wasm package db: installed with `wasm32-wasi-cabal install --lib hashtables hashable` and passed by `program.json` (`-package-db ~/.ghc-wasm/.cabal/store/ghc-9.14.1.20260731-70e7/package.db`, an absolute path) |
| dart | BG Dart #3 (dart exe): 32 codes per Uint64List word, HashMap<int,int> | isolates → in order; stdin pipeline → the same `LineSplitter` pipeline, synchronous; `find` prints 0, not `null`, for an absent fragment (BG's own n=1000 check output says 0) |
| js | BG Node #3 | workers → in order, Uint8Array not SharedArrayBuffer; **bug fix**: `frequency` stopped `length` windows early (`i < n`; at n=1000 BG's check output has T 31.520, Node #3 prints 31.500) |
| kotlin | not on BG: from BG Java GraalVM #1 (fastutil Long2IntOpenHashMap, keys recomputed per window, strided tasks) | fastutil is JVM-only: a minimal Long2IntOpenHashMap written the same way (linear probing, fastutil's mix, 0 key apart, 0.75 load); tasks in order; `%.3f` by hand |
| moonbit | not on BG: from BG Rust #7 | core `@hashmap.HashMap` (Int keys ≤12 codes, Int64 for 18); `%.3f` by hand |
| assemblyscript | not on BG: from BG gcc #1 | khash written in the file (power-of-two buckets, quadratic probing, `k ^ k>>7`, 0.77 load, insert-only); `%.3f` by hand |
| utu | gcc #1's algorithm, idiomatic utu | input in `mem src: U8`, codes in `mem poly: U8`; khash as a `mod Table` over `Array[I64]`/`Array[I32]` (same probing, hash, load); insertion sort of the ≤16 1/2-mers; F32 percentages; `%.3f` and output hashed as formatted. No `@wat`, no tuned variant |

SIMD: none (no port uses it here).

## Caveats

- Three BG programs had small counting bugs that BG's 25M output hides but these sizes show (C++ #2 and Go #7 window keys, Node #3 last windows); they are fixed here so all ports agree. Swift #2 needs 64-bit Int.
- The hash tables differ by language, which is most of this benchmark: khash (C, AssemblyScript, utu), pb_ds cc_hash_table (C++), hashbrown (Rust), Go maps of `*int`, Swift Dictionary, hashtables' Basic (Haskell, recomputing every key), Dart HashMap, JS Map of objects, a fastutil clone (Kotlin), MoonBit's HashMap.
- C++ ships iostream (`ostringstream`, 171 KB); Go, Swift, Haskell their runtimes (and `benchmarks/bg/wasi.js`); Dart and Kotlin their JS runtimes. JavaScript's size is its source only.
- Each port's fasta generator is in its Wasm (setup), so sizes include ~0.5–2 KB not part of k-nucleotide.
- `emscripten_notify_memory_growth`: Emscripten modules that grow memory import it; `benchmarks/bg/wasi.js` and the harness's generated loader now provide it as a no-op (it threw).


Update (2026-11-05): `knucleotide.utu` codes bases with a constant-array lookup (a `match` became a mispredicted br_table), fills the sequence by resize plus indexed writes (push inlined memory.grow into the loop), and keeps the hash table in one interleaved array (one cache line per probe): ~120 -> ~84 ms fastUnsafe. The previous version is `alt/knucleotide-before.utu`. utu numbers are in results.json.
